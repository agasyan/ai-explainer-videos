---
name: explainer-video
description: Make a narrated, animated explainer video from any sources (a topic, a PR, a repo or folder, a file, a recording, a web link, or an HTML page such as an internal report or a claude.ai artifact), as a 9:16 story and/or 16:9 landscape MP4. Writes an intent card and stops for approval, then writes the script, the voice, and drawn scenes (diagrams, infographics, 3D where it helps), renders 720p, and stops for the final approval; 1080p is optional. Use when the user asks for an explainer video, an animated explanation, a video about a PR, repo, document, or HTML page, a reel or story explainer, or to continue a video in projects/ or generated_videos/.
argument-hint: "<topic | PR | repo path | file | page.html | recording | link | project id> [--format story|landscape|both] [--moodboard <name>] [--video-format <name>] [--voice af_heart|am_michael|bf_emma|bm_george] [--length under-1m|1-3m|3-5m] [--parts 60s]"
---

Four steps, two stops: **1 Intent** (stop: the user approves `intent.md`), **2 Plan** (research, script, voice: no stop), **3 Preview** (scenes and the 720p video: stop, the final approval, which also covers the script and the voice), **4 1080p** (optional). For an existing project, run `make status SLUG=<id>` and continue from there. To ask: show the summary, then run `make approve SLUG=<id> STEP=<intent|preview>`. Claude Code asks the user, and that answer is the approval. If the user declines, apply their change and ask again. If the command is denied without a message (headless run), stop and end with `WAITING FOR APPROVAL: <id> <step>`. Editing an approved file cancels its approval; say what changed when you ask again. The tool refuses to make the voice or any picture until the intent is approved.

Each new video is a project, `projects/<YYYYMMDD>-<name>/`, made first; every file of its work stays inside it. Videos made before projects stay in `generated_videos/<slug>/` (no intent step); use the slug as it is.

Defaults: `landscape` (`story` if the user says IG, reel, story, phone, or TikTok), length 1-3 min (under 1 min for a story), one video with no parts, moodboard and video format recommended, voice `af_heart`, captions `pop`, 3D allowed where it explains better, viewer a smart colleague new to the topic.

**Sub-agents, for speed.** At most 5 per step, all spawned in one message so they run in parallel; more items than 5 means 2 per agent. Sub-agents start blank, so paste in each one: the objective, input file paths, the rules it needs, its output shape, and a status of `DONE`, `DONE_WITH_CONCERNS`, or `BLOCKED` plus the reason. Sub-agents never run `make approve`, `make narrate`, `make preview`, `make video`, `make new`, or `make from-html`, and never edit `intent.md`, `script.yaml`, `style.css`, or `approved.json`. The main agent keeps those. Without sub-agents, do the same work yourself.

1. **Intent: what the video says, to whom, and how.** Start the project first. When the request says `Slug: <id>`, the id is fixed: use exactly it in every command. Else use the name the request gives (`Name: <name>`), or a short kebab-case name, and the id the first command prints.
   - **Start:** a source that is an HTML page: `make from-html SLUG=<name> FILE=<absolute path>` (or, when the request says the page is copied already, `make from-html SLUG=<id>`). It copies the page and its CDN files, writes its text to `sources/page.md`, and makes `scenes/page-<id>.html`, a ready scene per page section for evidence. Any other source: `make new SLUG=<name> TITLE="<title>"`.
   - **Read every source into the project**, so it is complete on its own. The request lists sources as `kind, role: value`. Roles: **Main story** sources drive the story; **Context** explains around it; **Facts and numbers** are what the video may state; **Look reference** sets the look, not the content. Kinds: a topic is a question to answer; a PR: `gh pr view <n> --json title,body,files` and `gh pr diff <n>`; a repo or folder (read only): README, a depth-2 tree, entry points, 3 core files; a file: all of it (copy it to `sources/files/` when it is outside the repo); a recording: copy it to `sources/recordings/` when it is outside the project, then `make transcribe SLUG=<id>`; a web link: read it (needs web research on); an HTML page: `sources/page.md`. For 5 or more files or sections, spawn reader sub-agents, one per group: each writes `sources/<n>-<topic>.md` (facts with `path:line`, short quotes of the parts used) and returns 15 facts or fewer. Keep `sources/index.md`: one line per source, what it is, and where it came from (path, repo and commit, PR, or URL).
   - **Recommend the look and structure:** spawn one recommender sub-agent. Paste in the key message, the viewers, `moodboards/catalog.json`, `video-formats/catalog.json`, and this rule: return the best video format and the best moodboard for this message and viewer, plus 2 alternatives each, each with one line of why. A decision or a comparison leans to `compare` or `problem-fix`. A choice in the request (`Video format: x`, `Moodboard: y`) skips that catalog.
   - **The brief comes first.** When the request has one (`sources/brief.md`, or "the requester's brief" in the request), it says who watches (names and roles), why the video exists, what to cover, and what is known already. Build the intent from it; the sources fill in the facts. Names in it are for the intent's Viewers line: leave them out of the video unless the brief asks.
   - **Write `intent.md`**: replace every `(fill in`. Key message (one sentence, from the brief if there is one). Viewers: from the brief, else your guess from the sources. Sources: each with its kind, role, and what it gives. Story: the video format's acts, in order, one line each. Look: the moodboard and why, aspect, length, and where a diagram, an infographic, or 3D explains better. Keep and cut: what the video uses and what it leaves out. Evidence: page parts or screenshots to zoom into, or "none". Research: questions to look up, or "none".
   - **Rebuild, never replay.** An HTML page, a doc, or a recording is a source: retell its point in the video format's acts, shorter and simpler, with diagrams, stat cards, comparisons, and 3D where it helps. Do not follow the page's section order, and do not scroll the page. A page tour (every `scenes/page-<id>.html` in page order) only when the request asks for one.
   - Ask: `make approve SLUG=<id> STEP=intent`. Summary: the intent, in short.
2. **Plan: research, script, and voice (no stop).** Web research: when the request says `Web research: off`, use no web search or fetch, only the sources, and write no `research.md`. Else, for a topic or the intent's research questions: up to 5 researcher sub-agents, one per question group. Each opens every source it cites, takes each number and date from the page, and returns rows `| c<n> | claim | source 1 | source 2 | status |`; a claim needs two independent sources, else its status is `one source`. Write the rows to `research.md`, and give each beat that states a fact `sources: [c<n>]`. Write `script.yaml` yourself, in one voice: fill the brief from the intent, set `video_format:`, `moodboard:`, and `picks:` (the pick first), `three:` (`3D: off` means `three: false`), and shape the scenes by the acts and beat ranges in `video-formats/<name>/format.md`, each scene with a `treatment:` from `moodboards/<name>/moodboard.md` (or `page` for a `scenes/page-<id>.html` evidence scene). One beat is one visual change and 1 to 2 sentences. Make one video, and fit the length the request names, at about 140 words a minute: under 1 min is 140 words or fewer, 1-3 min is 140 to 420 words, and 3-5 min is 420 to 700 words. Cover a long source by saying less about each part of it, not by splitting. Split into parts only when the request asks for a length per part (`--parts 60s`): then each part is that long or less and opens with one sentence of context. Write `say` about 80% of the way to ASD-STE100: 20 words or fewer per sentence, active voice, one word per meaning, conversational. Sentence one is the payoff; the first scene names the parts before the process runs; the last beat is the win plus one next action. Spell out what the voice reads ("two percent", "A P I"); code and URLs go in `show` only. Wrap 1 to 2 key words per beat in `*asterisks*`. Run `make narrate SLUG=<id>` and fix until it prints no `CHECK`. State only facts you read; list guesses in `brief.guesses`. Do not stop: go on to step 3.
3. **Preview: drawn scenes, 720p.** Read `docs/visual-patterns.md` first: it maps each kind of content to a scene pattern (a verdict card, a scored table, a stat card, a step flow, a split view, a line that moves, a 3D infographic, a zoom into the evidence), with starter pages in `templates/patterns/`. Write `style.css` yourself first: one color per concept and the shared classes, on top of the moodboard (scenes link `/ev/theme.css` after `base.css`). Then spawn one scene sub-agent per scene. Paste in each: its scene id, its `treatment`, its beats (`id`, `say`, `show`), the pattern from `docs/visual-patterns.md` that fits each beat, the paths `moodboards/<name>/moodboard.md`, `ev/web/ev.js` (API comment), `ev/web/page.js` (for an evidence scene: `p.zoom` and `p.mark`), `docs/scenes.md`, `style.css`, and `templates/patterns/`, plus these rules. Draw with HTML, SVG, CSS, rough.js, KaTeX, or three.js (3D: `three: true` and a `three_why`; docs/scenes.md). Highlight only the element the voice names, when it names it; label each shape on the shape; show short labels, never the narration's sentences. Animate only with `EV.from`, `EV.to`, `EV.fromTo`, `EV.set`, and the helpers, timed with `EV.at(beat, "word")`. Keep content inside `.safe`: text blocks of 8 words or fewer, 2 or fewer on screen, one color per concept. Each scene agent writes only `scenes/<id>.html`, runs `make stills SLUG=<id> FORMAT=<f> SCENE=<scene>` (the frame before each next beat, linted, in seconds; never a full render), reads the contact sheet it prints, fixes up to 2 passes, and returns its status and `LINT` lines. Then run the full `make preview SLUG=<id> FORMAT=<f>` once. Run every `make` in the foreground with the longest timeout, and never end your turn to wait for a background command: a dashboard job ends when you stop, and its commands stop too. Spawn one reviewer sub-agent per contact sheet; each returns the frames that do not match their `show:`, or "all match". Fix what they report. At most 2 passes; done when:
   - [ ] zero `LINT` lines and zero JS errors
   - [ ] each frame shows what its `show:` says
   - [ ] zero frames look broken, empty, or cramped
   - [ ] the story follows the intent's acts, not a source's order
   Summary: the 720p MP4 paths, the contact sheets, any unticked box, and the `VERDICT 1080p:` line. Then ask for the preview approval: it approves the final video, the script, and the voice.
4. **Optional: 1080p.** After the approval, give the verdict from the `VERDICT 1080p:` line (also in `make status`) and ask the user: "Render 1080p? Verdict: <verdict>." Recommend no when it says "not needed"; recommend yes only when it says "worth it for big screens" and the video goes to a projector, a TV, or a public upload. Run `make video SLUG=<id> FORMAT=<f>` only on a yes. In a dashboard job (the request says "Dashboard job"), stop after the preview check: the page offers 1080p with the verdict. Summary: each MP4 path and length, plus the share check: zero customer data, zero secrets, audience internal or public.

Never edit `approved.json` or approve for the user. PRs, repos, HTML pages, recordings, and internal docs are confidential: put zero customer data or secrets in a video, and use fake example values. An evidence scene shows a page as it is, so zoom only into parts with no customer data, personal names, booking references, or links to private threads.
